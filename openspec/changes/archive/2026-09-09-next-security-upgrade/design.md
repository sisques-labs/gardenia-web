# Design: Next.js Security Upgrade (16.2.10 → 16.3.4)

## Technical Approach

Two exact version pins in `package.json` plus a regenerated `pnpm-lock.yaml`. No source file, `next.config.ts`, `Dockerfile`, or CI workflow changes. No bounded context is touched, so DDD/hexagonal layering is unaffected. Verification is the entire engineering content of this change: the risk is a silent 16.2 → 16.3 minor regression, not the edit itself.

## Architecture Decisions

| # | Decision | Alternatives rejected | Rationale |
|---|---|---|---|
| D1 | Pin `next` **and** `eslint-config-next` to `16.3.4` | `16.3.3` (strict minimum) | 16.3.3 ships AVIF optimization disabled; `eslint-config-next` never published 16.3.3, breaking this repo's lockstep parity invariant. Confirmed by the user. |
| D2 | Exact pins, no `^` range | Caret range | Repo convention: every dependabot/renovate sibling pin (#487–496) is exact. |
| D3 | Branch `fix/next-security-upgrade` off `dependabot/updates`, PR base `dependabot/updates` | Push onto `dependabot/updates` directly; branch off `main` | Never mutate PR #497's head. Basing on `dependabot/updates` makes the fix land inside the diff whose Trivy gate is failing. |
| D4 | Regenerate lockfile with `pnpm install --no-frozen-lockfile`, then re-verify with `--frozen-lockfile` | Hand-edit lockfile; plain `pnpm install` | Nested peer-dep resolution strings (`next@16.2.10(@babel/core@…)(react@…)`) cannot be hand-edited. The explicit flag is env-agnostic (pnpm defaults `frozen-lockfile=true` when `CI` is set); the second run proves the Docker builder's `pnpm install --frozen-lockfile` will succeed. |
| D5 | Verify the AVIF path by probing `/_next/image` directly, not only by looking at a screen | Visual screen check alone | All 18 `<Image>` call sites pass `unoptimized` (15 files), so browsing a photo screen never exercises the optimizer. See correction below. |

### Correction to the exploitability narrative (does not change D1)

Uploaded photos are routed through the app's own route handler `app/api/image-proxy/[id]/route.ts` and rendered with `unoptimized`, so the browser never hits `/_next/image` for user content. The exposure is still real but server-side: the optimizer endpoint is enabled by default and `images.remotePatterns` allows `http(s)://<api-host>/(api/)?files/*/content`, plus same-origin relative URLs, so an attacker can reach the libheif/sharp AVIF decoder by calling `/_next/image?url=…` with an uploaded file. Remediation target is unchanged; the manual check is what this fact reshapes.

## Execution Sequence (for sdd-apply)

```bash
# 0. Pre-apply gate (closes the open research item — MUST run and record output)
gh api repos/vercel/next.js/releases/tags/v16.3.3 --jq .body
gh api repos/vercel/next.js/releases/tags/v16.3.4 --jq .body
gh api repos/vercel/next.js/compare/v16.2.10...v16.3.4 --jq '.commits[].commit.message' | rg -i 'breaking|avif|image'
# 1. Branch
git switch dependabot/updates && git pull --ff-only
git switch -c fix/next-security-upgrade
# 2. Edit package.json (two exact strings), then
pnpm install --no-frozen-lockfile
pnpm install --frozen-lockfile   # must be a no-op; proves the Docker builder passes
# 3. Verify
pnpm lint && pnpm tsc --noEmit && pnpm test:coverage && pnpm build
# 4. Optional local smoke (matches CI's docker-smoke-build)
docker build -t gardenia-web:next-1634 . && docker run --rm -p 3000:3000 gardenia-web:next-1634
```

Stop and report `blocked` if step 0 reveals any breaking change across 16.3.0, or if any command in step 3 fails.

## Manual Verification (AVIF path)

1. `pnpm dev`, log in, open `/{lang}/plants/{id}` (plant detail + `plant-photo-gallery`) — a real uploaded photo must render, and the lightbox must open it. This proves the `unoptimized` + image-proxy path.
2. Then probe the optimizer directly in the same session: `/_next/image?url=%2Fapi%2Fimage-proxy%2F{fileId}%3Ftoken%3D{token}%26spaceId%3D{spaceId}&w=640&q=75`. Expect HTTP 200 with an image `content-type` (`image/avif` or `image/webp` under an AVIF-accepting browser), not 400/500. A 400 here after the bump would be the 16.3.3-style AVIF disablement leaking into 16.3.4 and must be reported.

## Testing Strategy

| Layer | What | How |
|---|---|---|
| Static | Lint + types under new `eslint-config-next` | `pnpm lint`, `pnpm tsc --noEmit` |
| Unit | Existing suite regression | `pnpm test:coverage` — no new tests; there is no new behavior to drive RED |
| Build | Standalone output still emitted | `pnpm build`, Docker 2-stage build |
| Manual | Image render + optimizer endpoint | Steps 1–2 above |
| CI | Trivy CRITICAL gate clears | PR run of `docker.yml` (`scan_image: true`) |

## Commit / PR Shape

Single commit, single PR, no AI attribution.

- Commit: `fix(deps): bump next to 16.3.4`
- PR title: `fix(deps): bump next to 16.3.4`
- PR base: `dependabot/updates` — PR head: `fix/next-security-upgrade`
- PR body:

```markdown
Bumps `next` and `eslint-config-next` from 16.2.10 to 16.3.4.

Closes GHSA-2xp9-vwfh-vxw4 (AVIF Image Optimization RCE, CVSS 9.5), which is
blocking the Trivy `block_on_critical` gate on #497. Also covers
CVE-2026-75604 (Windows-only cache path traversal, not exploitable on this
Linux runtime).

16.3.4 rather than the strict-minimum 16.3.3: 16.3.3 ships with AVIF
optimization disabled, and `eslint-config-next` never published a 16.3.3.

Verified: `pnpm lint`, `pnpm tsc --noEmit`, `pnpm test:coverage`, `pnpm build`,
Docker standalone build, and a manual `/_next/image` probe against an uploaded
photo.
```

## Threat Matrix

N/A — no routing, shell, subprocess, VCS/PR automation, executable-file classification, or process-integration boundary is introduced by this change. The `git`/`gh` commands above are operator steps, not shipped code.

## Migration / Rollout

No migration. Rollback is `git revert` of the single commit followed by `pnpm install --no-frozen-lockfile`.
